## 4. On Robert's go

1. **Create the pod** (the smoke's third shape, the one that worked): A100 SXM 80 GB, secure cloud, image
   `runpod/pytorch:2.8.0-py3.11-cuda12.8.1-cudnn-devel-ubuntu22.04`, `minCudaVersion 12.8`, **container disk
   160 GB, no volume** (the 150 GB volume came up full twice in the smoke), SSH port 22.
2. **Send the kit**: `runpodctl send runs/t1/t1-kit.tgz` on the Mac; on the pod
   `mkdir -p /workspace && cd /workspace && runpodctl receive CODE && tar xzf t1-kit.tgz`.
3. `bash benchmarks/training/t1/pod_setup.sh` → `SETUP OK`.
4. `bash benchmarks/training/t1/pod_train.sh` → the size check, then the run. Read the first rows of
   `runs/t1.log`: the step-0 validation loss, then step 1 (first loss near 0.3, not 12.4; peak under 80 GiB).
5. Watch `runs/t1/metrics.jsonl`: `tokens_per_second`, `loss`, the `eval_loss` rows at 64, 128, … Below
   2,400 tokens/s after the first steps, the run will not finish inside the cap: decide then, not at hour 19.
6. When the log stops: `bash benchmarks/training/t1/pod_finish.sh` → `FINISH OK`, then
   `runpodctl send runs/t1-back.tar` and receive it on the Mac into `runs/t1/`. Check the GGUF's sha256
   against `runs/t1-gguf.sha256`.
7. **Delete the pod** once the hash matches. Read `list-pod-billing` the next day for the real bill.

**The one risk of this shape:** with no volume, everything lives on the pod's container disk. If the pod is
lost or stopped mid-run, the checkpoints go with it and the money spent is gone. Secure cloud pods rarely
die in 19 h, and the smoke's volume failure is why the volume is off.

## 10. The conversion gap: LM Studio's repeat penalty (2026-11-24)

The base through our conversion sat 13.9 below the hub base on d1-dev (50.3 against 64.2, separated). The
cause is a sampling setting, not the file. LM Studio runs the hub file (`qwen/qwen3.5-9b`) with repeat
penalty 1.0 and gives an imported file its default 1.1; the harness sent neither, so every run of our own
files (`qwen3.5-9b-t1`, `-t1-smoke`, `-t1-v2`) was sampled with a penalty the hub base never had.

- Probe (temperature 0, seed 7, one prompt, three requests each: nothing sent, `repeat_penalty` 1.0, 1.1):
  on `qwen3.5-9b-t1` the default answer equals 1.1 and differs from 1.0; on the hub file it equals 1.0 and
  differs from 1.1.
- The template is not it: the first-turn prompt has the same token count in both runs on all 50 tasks.
- The rerun: the same file with `repeat_penalty` 1.0 sent (models.json `qwen3.5-9b-t1-rp1`), d1-dev,
  09:55 to 11:01: **65.2**. Against the hub base +1.0 (-4.2 to +6.5), not separated; against its own run at
  1.1, +14.9 (+5.9 to +24.4), separated. Our merge and quantization reproduce the hub base.

So the runs of §9 handicapped T1 by the same setting. T1 at 1.0 is `qwen3.5-9b-t1-v2-rp1`
(queue `queue-2026-11-24-ckpt-qwen3.5-9b-t1-v2-rp1-pin1`, the three dev sets).
