At the smoke's measured 2,400-3,000 tokens/s on the A100 SXM 80 GB ($2.19/h, read 2026-11-20):

| part | hours |
|---|---:|
| setup (install, llama.cpp build, kit transfer) | ~0.5 |
| training, 156.0M tokens | 14.4-18.1 |

## 3. The kit (built, on the Mac)

`runs/t1/t1-kit.tgz` (191 MB, gitignored; sha256 `91a8b00c…64ff`): the six `scripts/training_*.py`,
`results/training/` (the 42 conversation files, `tools.json`, `tokens.json`), the 9B's tokenizer folder, and
the three pod scripts in `benchmarks/training/t1/`:

| script | does |
|---|---|
| `pod_setup.sh` | the smoke's install with §8's fixes (torch 2.9.1 cu128 first, pinned versions, cmake, the llama.cpp UI patch) |
| `pod_train.sh` | the size check (must print 3,064 kept and 155,993,487 tokens, or it stops), then the run under the 19 h cap; `--resume` continues from the newest whole checkpoint |
| `pod_finish.sh` | merge → Q4_K_M → `check.json` → render check on the real file → `runs/t1-back.tar` |

The pod scripts are the smoke's steps written down from its record; they have not themselves run on a pod.
`pod_setup.sh` ends by printing the versions, so a drift from the smoke's shows in the first 15 minutes.

Rebuild the kit after any change to the scripts or the dataset:

```bash
cd "/Volumes/RobertsExternalSSD/repos/CAD Testing" && mkdir -p runs/t1/kit && rm -rf runs/t1/kit/tokenizer && cp -R ~/.roaddraft/tokenizers/Qwen3.5-9B runs/t1/kit/tokenizer && COPYFILE_DISABLE=1 tar --no-xattrs -czf runs/t1/t1-kit.tgz scripts/training_*.py benchmarks/training/t1/pod_*.sh results/training/*.jsonl results/training/tools.json results/training/tokens.json -C runs/t1/kit tokenizer
```

## 4. On Robert's go

1. **Create the pod** (the smoke's third shape, the one that worked): A100 SXM 80 GB, secure cloud, image
   `runpod/pytorch:2.8.0-py3.11-cuda12.8.1-cudnn-devel-ubuntu22.04`, `minCudaVersion 12.8`, **container disk
   160 GB, no volume** (the 150 GB volume came up full twice in the smoke), SSH port 22.
2. **Send the kit**: `runpodctl send runs/t1/t1-kit.tgz` on the Mac; on the pod
   `mkdir -p /workspace && cd /workspace && runpodctl receive CODE && tar xzf t1-kit.tgz`.
3. `bash benchmarks/training/t1/pod_setup.sh` → `SETUP OK`.
4. `bash benchmarks/training/t1/pod_train.sh` → the size check, then the run. Read the first rows of
   `runs/t1.log`: the step-0 validation loss, then step 1 (first loss near 0.3, not 12.4; peak under 80 GiB).
5. Watch `runs/t1/metrics.jsonl`: `tokens_per_second`, `loss`, the `eval_loss` rows at 64, 128, … Below
   2,400 tokens/s after the first steps, the run will not finish inside the cap: decide then, not at hour 19.
6. When the log stops: `bash benchmarks/training/t1/pod_finish.sh` → `FINISH OK`, then
   `runpodctl send runs/t1-back.tar` and receive it on the Mac into `runs/t1/`. Check the GGUF's sha256
   against `runs/t1-gguf.sha256`.
7. **Delete the pod** once the hash matches. Read `list-pod-billing` the next day for the real bill.

**The one risk of this shape:** with no volume, everything lives on the pod's container disk. If the pod is
lost or stopped mid-run, the checkpoints go with it and the money spent is gone. Secure cloud pods rarely
die in 19 h, and the smoke's volume failure is why the volume is off.
